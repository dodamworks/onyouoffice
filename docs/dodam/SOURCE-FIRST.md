# Required source-first preflight

Apply this preflight at the start of every task, before designing a replacement, adding a tool, implementing a change or preparing a commit/PR. Complete the checks autonomously within the user's authorized scope; this is not an additional approval gate.

1. Read the root and affected-module agent instructions and relevant project documentation. Maintainers also apply their private workspace boundary when present; external contributors do not need company account configuration.
2. Locate the affected implementation and resources in this Onyou Office checkout. Inspect the matching IeumOffice source or read-only reference before assuming a mechanism or asset is missing. Use the codebase map to find the relevant modules; do not substitute a new design or tool for an uninspected existing implementation.
3. Trace the source of truth, generators, generated outputs, actual consumers, tests and applicable contracts. For branding, include product.ts, build/brand SVGs, gen-brand-assets.mjs, AiMark.tsx, theme/locale rules, file-type icons, fonts and NOTICE. For other work, perform the equivalent trace in the affected area.
4. Record the inspected paths/revision, current fork differences, what can be reused, and what remains unverified in the task's project record. Claims that something is absent must identify the locations searched. Reuse still-current evidence; repeat only the affected checks when the source or scope changes.
5. Inspect a generator's write destinations before running it. Test in an isolated scratch tree when evaluating it. Keep the reference checkout, its frozen indexes, profiles and dependencies unchanged. Do not fetch, merge or modify upstream merely to perform this preflight; pin public source reads when a newer revision must be checked.
6. Define the smallest justified change and validation scope, then proceed. Preserve existing editor capabilities, internal package/IPC/document identifiers and user data. Validate the changed path rather than rerunning unrelated product suites for static assets or documentation.
7. Before a commit/PR, confirm that the submitted assets and documentation reflect the latest reviewed result and the inspected implementation contracts. Separate a source asset, generated output, app integration and OS/runtime validation; do not claim one from another.

Follow [the general change-impact CI policy](CI-POLICY.md). A user-approved exception for one asset-only PR does not establish a default skip policy. Non-runtime reference material receives its dedicated checks. Known test-entry-only changes follow the unit-only or E2E-only plans in CI-POLICY.md; product, configuration, shared-helper and unverified changes retain full checks. This preflight and the CI policy itself require full CI when changed. Do not expand CI policy as a side effect of this preflight.
